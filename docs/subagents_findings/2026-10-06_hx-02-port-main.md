## 1. Supply chain (R13.1-R13.3)

- `requirements/image-{constructor,core,full}.lock.txt` come only from `python scripts/lock_images.py` (`uv pip compile --generate-hashes --only-binary :all:`, CPython 3.11, x86_64 Linux) against main's `pyproject.toml`. Two runs are byte-identical. litellm 1.104.0, poetry-core 2.5.0 (via `requirements/build.in`).
- `uv.lock` regenerated with `uv lock`: netie 0.1.0 -> 2.5.0, requires-dist equal to pyproject.
- Each Dockerfile: `pip install --only-binary :all: --require-hashes -r requirements/image-<variant>.lock.txt`, then `pip install --no-deps --no-build-isolation <extras>`.
- `scripts/check_supply_chain.py` (offline) in `ci.yml`. On main's own `uv.lock` and Dockerfiles it reports 43 problems (31 uv.lock drift, 12 Dockerfile) and exits 1.

## 2. Egress chokepoint invariant (R2.5)

**Adaptation.** #283 required every provider entry point to sit inside `with CortexOS.integrations.harness.gate.call(...)`. That gate (HX-03) is not on main. Main's gate is the OpenVault FreeRoute client, `CortexOS.integrations.freeroute.complete`, which POSTs to OpenVault `/v1/chat/completions` over stdlib HTTP and needs no provider SDK. So on main any provider entry point (litellm, Anthropic/OpenAI SDK, Gemini, Bedrock) or provider host literal in `CortexOS/**` or `packs/**` is an OpenVault bypass. Calls through `freeroute.complete` / `crew.freeroute.complete_core` are never flagged.
