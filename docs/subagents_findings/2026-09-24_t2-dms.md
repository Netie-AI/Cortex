# T2-DMS: role gates on the DMS query, chat, warehouse and task routes (#263)

Epic #263 (EPIC-TRUST-02), ticket T2-DMS. Reuses the TRUST-01 auth port (`CortexOS/security/auth_port.py`, finding `2026-09-24_trust-01.md`). Base: 636e99b.

## Expected vs actual (before this change)

- Expected: every route registered by `CortexOS/api/dms_query.py`, `chat_routes.py`, `warehouse_routes.py` and `task_routes.py` refuses a caller with no key (401) or too low a role (403) before its handler runs, and a refused request changes nothing. The actor or approver written to the ledger, the task-event table and the changelog is the authenticated caller.
- Actual: none of the 24 routes had an auth dependency. Any caller that could reach the port could ask questions, read the audit trail and tables, write the changelog and the inventory CSV, open chat threads, create locations, take items in, move them, confirm dimensions (including overriding the free-capacity gate), and create or acknowledge compliance-gated task events. The actor and `approved_by` values were copied from the request body, so the ledger recorded whatever name the caller typed.

## Root-cause class

Missing authorization on an engine route plane, plus identity taken from untrusted input (body-supplied actor). Same class as TRUST-01 for `/api/apps`.

## Fix

All four modules use `require_role` from the engine port, in the same style as `app_routes.py` (`dependencies=[Depends(require_role(...))]`), with the principal injected as a parameter where the handler needs the actor. No `packs.*` import was added; `dms_query.py` still has none.

| Route | Role |
|---|---|
| `POST /dms/query`, `GET /dms/audit`, `/dms/tables`, `/dms/table-preview`, `/dms/data/{variant}`, `/dms/changelog`, `POST /dms/analyse-entry` (pure parse, no write) | viewer |
| `POST /dms/propose-edit`, `POST /dms/add-entry` | steward, `approved_by` = caller |
| `GET /dms/threads/{id}/messages` | viewer |
| `POST /dms/threads`, `POST /dms/threads/{id}/messages` | steward, actor = caller |
| `GET` location tree, QR label, space, by-code | viewer |
| `POST /dms/warehouse/locations`, `/dms/items/estimate-dims` (intake step, large untrusted upload) | steward |
| `POST /dms/items/intake`, `/dms/movements/scan`, `/dms/items/{id}/confirm-dims` | steward, actor = caller |
| `confirm-dims` with `gate_approved: true` (overrides the capacity gate, an approval) | admin, re-authorized before any write, actor = the admin |
| `POST /dms/tasks/gate/check`, `/choose`, `/gate/acknowledge` (all write the task-event table and ledger) | steward, actor = caller |

The `actor` and `approved_by` body fields stay on the models unchanged (same default, same schema), so existing clients still validate and the component schemas vendored in `contract/openapi-1.2.0.json` do not drift. They are ignored by the handlers.

## Invariant

Every route in these four modules refuses before its handler runs unless the registered authorizer grants the route's minimum role; no authorizer means 503. The ledger and changelog identity on these routes is the authenticated principal, never request input.

## Known limitations (not regressions for key-holding callers)

- The demo UI opens the QR label through a plain link (`href={warehouseQrLabelUrl(...)}`), which cannot carry a header, so with auth enabled the label gets 401. It still works with `DMS_AUTH_DISABLED=1`. Fixing it needs a UI change outside this ticket (fetch the PNG with the header, or a scoped cookie).
- The demo UI passes role names as `actor` / `approved_by`; those are now ignored, and the ledger shows the key's actor (`api_steward`, `api_admin`, or `auth_disabled` when auth is off).
- `POST /dms/tasks/gate/check` still accepts `human_acknowledged` inside `filled_template`. Both check and acknowledge need steward, so this grants nothing beyond what acknowledge grants.
- Observed, not changed: `add_inventory_entry` inserts 8 values into a warehouse `inventory` table that currently has 12 columns, so a real add-entry fails at the DuckDB insert after writing the CSV and changelog. The tests stub the warehouse connection. Out of scope for an auth ticket.
- `tenant_id` on these bodies is still caller-supplied. Tenant binding is not part of this ticket.
