# H2-DLOG-MP: decision log fork-safe and proven across processes (#255)

Epic #249 EPIC-HARDEN-2. Base 275fe13. Worktree lane wf_41d6fc93-b7a-6.

## Expected vs actual

Expected (issue #255): a forked child never inherits a held decision-log lock;
4 processes x 8 threads appending to one `tier_decisions.jsonl` produce exactly
the expected number of lines, every line valid JSON, none torn or interleaved;
the writer never raises and every failure is counted.

Actual on 275fe13 (`CortexOS/decision/decision_log.py`): `append()` held the
module-level `threading.Lock` across `mkdir`, `open("a")` and `write`. A fork
taken while any writer thread was inside that window left the child with a lock
that is held forever (the holding thread does not exist in the child), so the
child's first `append()` blocked on `with _lock:` and never returned. Reproduced
with the new fork test: 12 of 12 forked children hung past a 15 s timeout each.
Multi-process appends had only been assumed safe (KEV-LOG finding, "ASSUMED").

## What was built

- `CortexOS/decision/decision_log.py`:
  - `os.register_at_fork(after_in_child=_reset_lock_after_fork)` (guarded by
    `hasattr(os, "register_at_fork")`, so Windows imports unchanged) replaces the
    module lock with a fresh unheld one in every forked child.
  - `_write_line()`: each line is one `os.write` on a descriptor opened with
    `O_WRONLY | O_APPEND | O_CREAT | O_CLOEXEC`. This is the O_APPEND
    single-write option from the ticket, not a file lock: POSIX positions every
    O_APPEND write at end-of-file atomically, so lines from different processes
    and threads land whole and in some total order. A short write raises and is
    counted as a failure rather than leaving a torn line silently.
  - The lock is no longer held during the write at all; it now only guards the
    failure counters. The kernel serialises the writes, which a process-local
    lock could never do across processes anyway.
  - Module docstring documents the concurrency contract.
- `tests/test_decision/test_decision_log_mp.py` (new, 4 tests):
  - 4 spawned interpreters x 8 threads x 25 lines (800 lines) with a file start
    barrier plus a per-process `threading.Barrier`. Asserts: every worker
    reported every append written and `write_failures() == 0`; the file has
    exactly 800 lines; the file ends in a newline; `json.loads` on every line;
    per-writer count is exactly 25 for all 32 writers; every (writer, index)
    pair appears once; at least 20 process switches and 100 writer switches
    between adjacent lines, so the writers demonstrably contended.
  - Fork-while-writing (POSIX only, skipped with a loud reason elsewhere): a
    subprocess runs 8 hammering writer threads and forks 12 times; each child
    appends 20 lines and `_exit`s; the parent `waitpid`s with a 15 s timeout
    and kills a hung child. Asserts rc 0, `hung == []`, every child's 20 lines
    present in the file, parent lines present after the first child line.
  - 8 threads on a path that is a directory: `append()` never raises, returns
    False 200 times, `write_failures() == 200`, `last_write_error()` set.
  - Held-lock fork (POSIX only; added for the verifier finding below): a
    subprocess sets the log path to a directory so every append fails and must
    take `_lock` to count the failure, acquires `decision_log._lock` in the
    parent (a writer thread inside the counter section at fork time), forks;
    the child calls `append()`, checks the failure was counted, calls
    `reset_write_failures()` and `_exit`s 0 only when the counter is back to 0.
    The parent `waitpid`s with `WNOHANG` and a 15 s timeout and kills and
    reports a hung child. Asserts rc 0, last stdout line `child exit 0`, and
    nothing written under the blocking directory.

## Verifier finding (blocking) and fix

Finding: no test covered acceptance line 1 (the child resets the log lock via
`os.register_at_fork(after_in_child=...)`). A mutant with that registration
replaced by `pass` passed all 3 tests, because the write path no longer takes
`_lock` at all: the fork-while-writing test only failed on base because base
held `_lock` across the file I/O. The hook worked on HEAD but nothing enforced
it.

Fix: `test_child_forked_while_lock_is_held_gets_a_fresh_lock_and_working_counters`
forces the child onto the only remaining locked path (failure counting) with
the lock held at fork time.

Mutant check, run in this worktree (mutant = HEAD with the
`os.register_at_fork(after_in_child=_reset_lock_after_fork)` line replaced by
`pass`, file swapped in, run, HEAD restored):

```

mutant (hook removed):     1 failed in 15.30s  (rc=1)  stdout: child HUNG on the lock inherited across fork
base 275fe13 file:         1 failed in 15.29s  (rc=1)  stdout: child HUNG on the lock inherited across fork
```

The test fails when the register_at_fork line is removed; the hook is now a

## Root-cause class

Fork-unsafe lock discipline: a process-local mutex held across I/O and inherited
across `fork()`. Secondary: an untested assumption (cross-process append safety)
recorded as such but never converted into a gate.

## Invariant

- A forked child of any Cortex process can append a decision line; it never
  blocks on state inherited from the parent.
- Concurrent appenders (threads or processes) never tear or interleave a line;
  the line count equals the number of successful `append()` calls.
- `append()` and `log_decision()` never raise; every failed write increments
  `write_failures()`.
- Do-not-touch list respected: no change to `shadow.py`, `labels.py`,
  `CortexOS/execution/**`, `tests/test_decision/test_decision_log.py`,
  `tests/conftest.py`, `tests/contract/**`, `tests/invariants/**`,
  `.importlinter`, `contract/**`. `CortexOS/**` still imports no `packs.*`.

## Coordinator fix at integration (2026-09-24)

On the integration branch, the full suite failed once: `only 3 process switches in 800 lines; processes did not contend`. The machine was loaded because a parallel workflow was running.

- Root cause: the harness comment "every interpreter is up" was false. The parent touched the go-file right after `Popen`, before the child interpreters had imported the module, so the first child to finish importing wrote most of its lines alone.
- Fix, a two-phase barrier: each worker writes `go.ready.<proc>` after import, and the parent opens the gate only when all are ready (it fails loudly if a worker dies first). A 1 ms yield between appends means writers hand the file over even under CPU pressure.
- Evidence: before the fix, 1 of 6 parallel runs failed. After it, 16 of 16 passed with 8 copies running in parallel.
- This is a test-harness defect, not a decision-log defect. The single-write O_APPEND lines were whole in every run.
