|---|---|---|
| SQLite writers from separate processes wait, never fail | `_connect` sets an explicit busy timeout of at least 30 s | `sqlite3.connect(str(path), check_same_thread=False)` with no timeout (module default 5 s), `ledger.py:101` |

## Repro (verified in this run)

Forcing the busy timeout to 0 in four child interpreters, each appending 25 entries
to one file through the public API:

```
worker error: sqlite3.OperationalError: database is locked
worker error: sqlite3.OperationalError: database is locked
rcs [0, 0, 1, 1] entries 50 verify VerifyResult(ok=True, broken_at=None)
```

Two of four processes die, 50 of 100 entries are lost, and `verify().ok` is still
true because the chain that survived is internally consistent. So `verify()` alone is
not a concurrency proof; the row count and seq range must be asserted too. The new
test asserts both, and the row-level `prev_hash == previous entry_hash` link.

With the 30 s timeout in place the same 4x25 run yields 100 rows, seq 0..99, verify ok.

Correction after adversarial verify: with SQLite's stock 5 s default (no explicit timeout, as on 7e14ec1) the 4x25 run also passes on this host, so the multiprocess test alone does not distinguish the fix. The loss above needs the timeout forced to 0. The 30 s value is headroom for heavier contention and is proven set only by `test_connect_sets_busy_timeout_of_at_least_30s`. What the multiprocess test does prove is that the cross-process path (BEGIN IMMEDIATE on the file lock, not the in-process thread lock) keeps a gap-free verified chain. Contention is now real and asserted: a start barrier (a go-file the parent touches after all workers start) plus a 1 ms yield between appends. Measured worker switches in 100 rows: 4, 4, 6 before (the barrier alone did not help, a lock holder appends in a burst); 41, 51, 54 with the yield. The test asserts at least 10 switches, so it fails if the writers stop contending.

CI skip hole, reproduced locally with `DMS_LEDGER_DSN` unset:
`pytest tests/dms/test_f1_ledger.py -k postgres` exits 0 with `3 skipped`. The new
junit check step reads the XML and exits 1 with
`skipped=['test_postgres_chain_append_and_verify_ok', ...]`.

## Root-cause class

Proof gap, not a chain bug. The serialisation mechanisms were correct (`BEGIN IMMEDIATE`
on SQLite, `pg_advisory_xact_lock` plus `FOR UPDATE` on Postgres) but were never
exercised by anything that could fail: the SQLite test could not reach the file lock
past the process-local thread lock, and the Postgres tests were never selected by a job
that had a DSN. A green job that runs zero of the tests it claims to prove is the
"gate that cannot fail" pattern from CLAUDE.md section 7.

## Change

1. `packs/dms/audit/ledger.py`: new constant `SQLITE_BUSY_TIMEOUT_SECONDS = 30.0`;
   `_connect` passes it as `timeout=` and also executes `PRAGMA busy_timeout = 30000`
   so the value is observable on the connection. No change to append, verify, hashing
   or schema.
2. `tests/dms/test_f1_ledger_multiprocess.py`: asserts `PRAGMA busy_timeout >= 30000`
   on a `_connect` connection; spawns 4 `python -c` workers (spawn-safe, no import of the
   test module by name, `DMS_LEDGER_DSN` removed from the child env) that each append 25
   entries via `ledger.append`; asserts `verify().ok`, 100 rows from `list_entries`,
   seq exactly 0..99, unique ids and hashes, `prev_hash` chain links, and 25 rows per
   worker.
3. `.github/workflows/rls.yml`: three new steps after the RLS deny proof. Run the
   `-k postgres` ledger tests with `--junitxml`; a Python step parses the junit file and
   exits 1 if any of the three named tests is missing, skipped, failed or errored;
   then run the multi-process SQLite test with `DMS_LEDGER_DSN=""` (which
   `ledger_dsn()` treats as unset) so the SQLite path is what runs.

## Invariant applied

Fail closed on the proof itself: a job that proves ledger integrity must fail when
the proof did not run. `verify()` is necessary and insufficient; the user-visible rows
(count, seq, prev_hash links) are asserted alongside it. No `CortexOS/**` file touched,
no `packs.*` import added to the engine, no contract change, no change to
`tests/dms/test_f1_ledger.py` or `packs/dms/sql/**`.

## First real CI run of the Postgres proof found a production bug (2026-09-23)

The new must-PASS step did its job on its first run (rls-proof on 296c34b): `test_postgres_chain_append_and_verify_ok` and `test_postgres_concurrent_appends_consistent` FAILED with `TypeError: the JSON object must be str, bytes or bytearray, not dict`.

- **Expected:** a Postgres ledger migrated in the documented order appends and verifies.
- **Actual:** two migrations define `dms_audit_ledger`. `001_warehouse_v0.sql` uses `payload JSONB` and `created_at TIMESTAMPTZ`. `002_ledger_postgres.sql` (the schema `ledger.py` was written for) uses TEXT, and its `CREATE TABLE IF NOT EXISTS` is a no-op once 001 ran. `_postgres_verify` then called `json.loads` on the JSONB dict. With that fixed alone, verify still reported the chain **broken** on an untouched ledger (a false tamper alarm), because a TIMESTAMPTZ read back as a `datetime` in the session time zone never equals the ISO string that was hashed.
- **Repro:** fresh Postgres 16, run `tests/dms/test_rls_blocks_out_of_scope_read.py` (applies 001+002+003+007), then `pytest tests/dms/test_f1_ledger.py -k postgres`: 2 failed. On a fresh DB that only the ledger initialises (TEXT columns) the same tests pass, which is why it never showed up before.
- **Root-cause class:** schema drift. One table has two DDL definitions, and the code was only ever exercised against one of them.
- **Fix:** read side in `ledger.py`. `_stored_payload` accepts a decoded dict or TEXT JSON. `_stored_created_at` renders a `datetime` back to the UTC ISO string used at append (appends drop microseconds). Both are used by `_postgres_verify` and `_row_to_entry`. The migrations are unchanged (shared DMS schema, outside this ticket).
- **Test:** `tests/dms/test_f1_ledger_pg_migrated_schema.py` migrates 001+002 into an isolated schema with session time zone Asia/Kuala_Lumpur and asserts the column types are jsonb/timestamptz, that `verify().ok` holds, that payloads round-trip, and that `created_at` is ISO UTC. It fails on the pre-fix code with the same TypeError. With only the payload half fixed, it fails with `verify().ok is False`. The RLS CI step runs it and the must-PASS check lists it.
- **Invariants:** "Prove a gate can fail before trusting it green" (the gate's first run caught a real bug); "Fix the root-cause class": both drift symptoms fixed, and the drift itself (two DDLs for one table) is flagged for a DMS migration follow-up.
- **Residual / follow-up:** reconcile 001 and 002 into one ledger DDL in a DMS migration. That is a schema decision for the DMS lane.
