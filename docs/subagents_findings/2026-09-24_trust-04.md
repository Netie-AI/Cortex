# TRUST-04 (#260): reap orphaned workflow runs so they can be resumed after a restart

Epic: #256 EPIC-TRUST-01. Base: 4f74c0f.

## Expected vs actual

- Expected: after an engine restart, a workflow run that was queued or running in the dead process shows in the Background tasks panel as `error` with an "interrupted, resumable" message, is no longer listed as active, and Resume re-runs it, replaying the nodes the step journal already holds.
- Actual (base): the `wf_runs` row stays `queued`/`running` forever. `list_runs(status="active")` keeps returning it, so the panel shows a dead run as live. `resume()` refuses any row whose persisted status is `running` ("run is still active"), and `_ensure_loop` never reconciles, so the only way out was a manual cancel.

## Root-cause class

Durable state with no reconciliation after process death: in-process liveness (`_ACTIVE`, the loop thread) was never compared with the persisted status on startup.

## Fix

- `workflow_store.reap_orphans(active_ids, started_before)`: marks `queued`/`running` rows as `error` with `ORPHAN_ERROR` (contains "interrupted" and "resumable") only when the id is not in `active_ids` AND `COALESCE(started_at, created_at)` is strictly before `started_before`. Running phases and agents of a reaped run are closed as `error`. A `run_finished` event is published for each reaped run. With no orphans it writes nothing.
- `workflow_runner`: records `_PROCESS_STARTED_AT` at import (only this module creates runs, so every row this process creates is later). `_ensure_loop` reaps under `_LOCK` whenever it creates a new loop. `snapshot()` and `resume()` reap once per process before reading, so the panel and the first Resume after a restart see the reconciled status even before any new run started the loop. A reap failure is logged and swallowed so it can never block a new run.
- Resume panel fidelity: a replayed `node_done` event (no telemetry) previously left the agent row stuck at `running` after `agent_started`. The runner now calls the new `workflow_store.agent_replayed`, which restores `done` without re-counting tokens or cost and publishes an `agent_replayed` event with `replayed: True` to live listeners.

## Invariant

A run is reaped only if it is not live in this process and predates this process. A live run (in `_ACTIVE`) and any run created after this process started are never touched.

## Verified vs assumed

- VERIFIED: the tests above, `tests/test_workflow_runner.py` and `tests/dms/test_distill_engine_api.py` pass; full suite, ruff, lint-imports, contract tests (see the commit's gate results).
- ASSUMED / residual: in a multi-process deploy sharing one `runs.db`, a sibling engine that started earlier than this one and is still executing a run that also started earlier would be reaped (PRD risk, accepted scope). If that sibling later finishes, its `finish_run` overwrites the `error` status with its real result. A heartbeat column would close this and is out of scope.
- `activity_routes` reads `list_runs(status="active")` directly without going through the runner, so it shows a dead run as active until the first snapshot, resume or run start in the new process. Not in the write targets.
