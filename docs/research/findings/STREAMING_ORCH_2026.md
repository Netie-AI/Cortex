# Streaming, Durable Orchestration, Agent-on-Stream & Stress Testing — Research Findings (July 2026)

Researched 2026-07-20 for Cortex DMS (local-first, Windows 11 host, Python 3.10, FastAPI, DuckDB, SQLite/Postgres, Docker/WSL2 optional, $0 default infra).
Each claim tagged **VERIFIED** (primary/secondary source checked this session) or **INFERENCE** (reasoned from verified facts).

---

## 1. Lightweight streaming ingestion for a one-box Python stack

### Brokers

- **Redpanda** — C++ single-binary Kafka-API broker, no JVM/ZooKeeper, auto-tunes; p99 latency far below Kafka. **VERIFIED**: [Redpanda Kafka alternatives guide](https://www.redpanda.com/guides/kafka-alternatives), [PkgPulse 2026 comparison](https://www.pkgpulse.com/blog/redpanda-vs-nats-vs-apache-kafka-event-streaming-platforms-2026). **No native Windows binary — Docker/WSL2 only**; `rpk container` on WSL has open issues. **VERIFIED**: [Redpanda quickstart (Docker)](https://docs.redpanda.com/current/get-started/quick-start/), [redpanda#13331](https://github.com/redpanda-data/redpanda/issues/13331).
- **Apache Kafka (KRaft)** — Kafka 4.0 (Mar 2025) removed ZooKeeper; KRaft-only. Still JVM, still heavyweight tuning; highest ecosystem interop. **VERIFIED**: [Tinybird Kafka alternatives](https://www.tinybird.co/blog/apache-kafka-alternatives). **INFERENCE**: worst fit of the three for a 12-GB-GPU one-box Windows host.
- **NATS JetStream** — single ~10-20 MB Go binary, native Windows build (zip → binary), tiny config, sub-ms latency, JetStream adds persistence/replay/KV; moderate throughput vs Kafka (fine for one box). **VERIFIED**: [NATS install docs (Windows zip/choco)](https://docs.nats.io/running-a-nats-service/introduction/installation), [RisingWave NATS/Kafka/Redpanda comparison](https://risingwave.com/blog/nats-kafka-or-redpanda-which-real-time-data-solution-is-best/). Official Python client `nats-py` supports JetStream. **VERIFIED** (docs.nats.io).

### Python processing layers

- **Quix Streams** — pure-Python Kafka stream processing: pandas-like API, RocksDB stateful ops, windowing, exactly-once via Kafka transactions, Sources/Sinks API. **v3.24.0, 2026-06-12, Apache-2.0, actively developed, commercially backed.** **VERIFIED**: [quixio/quix-streams](https://github.com/quixio/quix-streams). Requires a Kafka-API broker (pairs with Redpanda). **VERIFIED**: [Redpanda + Quix walkthrough](https://redpanda-data.medium.com/stream-processing-in-python-with-redpanda-and-quix-aba90f89ba8c).
- **Bytewax** — Python API over Rust/Timely dataflow; strong parallelism, broker-agnostic connectors. **Community-maintained since 2025 after the backing company wound down** — maintenance risk. **VERIFIED**: [RisingWave Python streaming guide 2026](https://risingwave.com/blog/stream-processing-python-practical-guide/), [Bytewax roundup](https://bytewax.io/blog/stream-processing-roundup2/).
- **Faust / faust-streaming** — original Robinhood project abandoned; community fork `faust-streaming` limps along, not vendor-backed. **VERIFIED**: [Conduktor "Kafka Streams in Python"](https://www.conduktor.io/kafka-streams/python). Avoid for new builds. **INFERENCE**.
- **Arroyo** — Rust streaming-SQL engine; **acquired by Cloudflare Apr 2025**, now powers Cloudflare Pipelines; OSS engine still exists but v0.15.0 (Dec 2025) was the only H2-2025 release; roadmap is Cloudflare-driven, pre-1.0. **VERIFIED**: [Arroyo joining Cloudflare](https://www.arroyo.dev/blog/arroyo-is-joining-cloudflare/), [Cloudflare Pipelines blog](https://blog.cloudflare.com/cloudflare-acquires-arroyo-pipelines-streaming-ingestion-beta/), [RisingWave vs Arroyo](https://risingwave.com/blog/risingwave-vs-arroyo-rust-stream-processors/). Not a safe dependency. **INFERENCE**.
- **RisingWave** — Postgres-compatible streaming-SQL database; v2.8.1 (Mar 2026), GA, active. Has single-node/standalone mode but is a full stateful DB (RAM-hungry; Docker on Windows). **VERIFIED**: [Streaming DB landscape 2026](https://risingwave.com/blog/streaming-database-landscape-2026-complete-guide/). Overkill until Cortex needs continuously-maintained materialized views. **INFERENCE**.
- **Plain asyncio consumers → DuckDB/Parquet** — FastAPI already gives an async HTTP surface; a webhook endpoint + background writer batching appends into Parquet/DuckDB needs zero new infra. DuckDB appends never conflict (single-writer process, optimistic concurrency; concurrent appends OK, concurrent row-edits conflict). **VERIFIED**: [DuckDB concurrency docs](https://duckdb.org/docs/current/connect/concurrency). DuckLake v1.0 spec + implementation published Apr 2026 (production-intended lakehouse catalog over Parquet) — but concurrent-writer issues still open. **VERIFIED**: [ducklake#233](https://github.com/duckdb/ducklake/issues/233).

### Tiered recommendation

- **V0 (now, $0, no broker)**: FastAPI webhook/sensor POST endpoints → in-process asyncio queue → micro-batch writer appending Parquet (partitioned by hour) + DuckDB views. SQLite/Postgres ledger entry per batch for governance. Windows-native, zero new processes. **INFERENCE** from verified DuckDB append semantics.
- **V1 (light broker, still local)**: **NATS JetStream** as the buffer/replay layer — the only broker of the three with a native Windows binary; `nats-py` consumers feed the same batch writer. JetStream gives at-least-once, replay, consumer groups, KV for agent state. **INFERENCE** on fit; Windows support **VERIFIED**.
- **V2 (enterprise interop)**: **Redpanda in Docker/WSL2** (Kafka API without JVM ops) + **Quix Streams** for Python processing (windows, stateful ops, exactly-once). Drop-in interop with customer Kafka/Flink estates. **INFERENCE** on combo; components **VERIFIED** above.

## 2. Durable execution / workflow orchestration (parking-lot P3)

- **Temporal OSS** — gold standard durability; server + Postgres/MySQL/Cassandra + Elasticsearch for full deployments. Real-world single-node prod: 4 vCPU/16 GB (Hetzner CCX13) for low volume; <~100 wf/s per single server. Python SDK mature. **VERIFIED**: [self-hosted guide](https://docs.temporal.io/self-hosted-guide), [2026 self-host tutorial](https://automationatlas.io/guides/tutorial-temporal-selfhosted-deploy-2026/), [sdk-python](https://github.com/temporalio/sdk-python). Dev story is lighter than reputation suggests: `temporal server start-dev` = single cross-platform binary (Windows included), SQLite persistence via `--db-filename`, Web UI on :8233. **VERIFIED**: [dev server docs](https://docs.temporal.io/develop/run-a-development-server), [CLI setup](https://docs.temporal.io/cli/setup-cli). Still an extra always-on service + gRPC hop + worker model. **INFERENCE**.
- **DBOS Transact (Python)** — durable execution **as a pip library inside your process**; workflows/steps checkpointed to a system DB; on restart all incomplete workflows resume from last completed step. **SQLite is the zero-config default; Postgres recommended for production** (`DBOS_SYSTEM_DATABASE_URL`). MIT license. **v2.27.0 released 2026-07-14** — very active. Queues, cron scheduling, dynamic schedules, workflow patching/lineage (Mar 2026), Kafka consumer integration, OpenAI Agents SDK + Pydantic AI durable-agent integrations. Conductor control plane (optional, proprietary) adds dashboards/alerting + an MCP server for agent-driven ops. **VERIFIED**: [dbos-transact-py](https://github.com/dbos-inc/dbos-transact-py), [integrating DBOS docs](https://docs.dbos.dev/python/integrating-dbos), [What's New Mar 2026](https://www.dbos.dev/blog/dbos-new-features-march-2026), [Pydantic AI DBOS docs](https://ai.pydantic.dev/durable_execution/dbos/).
- **Hatchet** — Postgres-backed task orchestration (queues, DAGs, durable tasks, cron, web UI); Python/TS/Go SDKs; MIT; self-host = engine + Postgres + workers (Docker Compose). Heavier than a library, lighter than Temporal. **VERIFIED**: [hatchet-dev/hatchet](https://github.com/hatchet-dev/hatchet), [architecture docs](https://docs.hatchet.run/home/architecture).
- **Prefect 3 / Dagster** — **Prefect announced acquisition of Dagster Labs (July 2026); combined company operates as Prefect from Aug 2026; Dagster keeps its OSS license.** **VERIFIED**: [dagster.io/prefect](https://dagster.io/prefect), [BusinessWire 2026-07-13](https://www.businesswire.com/news/home/20260713065285/en/Prefect-Acquires-Dagster-Uniting-the-Two-Leading-Modern-Orchestrators). Both are batch/asset orchestrators with retries — not step-level durable execution (no deterministic replay/resume mid-function). Consolidation adds roadmap uncertainty this year. **INFERENCE**.

**Verdict for P3**: **DBOS Transact** is the Temporal-style durability with near-zero ops: same process, SQLite by default → the existing Cortex Postgres later, MIT, agent-framework integrations already shipped. Temporal stays the documented "scale-out escape hatch" (its dev server even runs Windows-native for experimentation). Hatchet is the middle option if Cortex later wants a queue UI + multi-worker fleet on Postgres. **INFERENCE** built on verified facts above.

## 3. Agent-as-employee orchestration patterns (mid-2026)

- **MCP is the settled tool-surface standard**: donated to the Linux Foundation's Agentic AI Foundation (Dec 2025) with OpenAI/Google/Microsoft co-sponsorship; ~97 M monthly SDK downloads by Mar 2026; ~10 k public servers; July 2026 spec RC adds stateless core, Tasks, Extensions, MCP Apps, authorization hardening; Enterprise-Managed Authorization extension now stable. **VERIFIED**: [MCP spec RC blog 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), [InfoQ EMA](https://www.infoq.com/news/2026/07/mcp-ema-enterprise-auth/), [Wikipedia/MCP](https://en.wikipedia.org/wiki/Model_Context_Protocol). → Expose Cortex capabilities (query, ledger, report writer) as MCP tools; any agent runtime can then "employ" them. **INFERENCE**.
- **Databricks (the managed benchmark to emulate, not buy)**: Agent Bricks GA at DAIS 2026 (Custom Agents, Supervisor Agent Feb 2026, Document Intelligence); **Genie Conversation API GA** (programmatic NL→insight conversations); Genie Spaces renamed "Genie Agents" July 2026. **VERIFIED**: [Agent Bricks blog](https://www.databricks.com/blog/agent-bricks-governed-enterprise-agent-platform), [Genie 2026 release notes](https://learn.microsoft.com/en-us/azure/databricks/ai-bi/release-notes/2026). Pattern to copy: governed agent registry + supervisor agent + conversation API over governed data. **INFERENCE**.
- **Event-driven agents are the production norm**: industry converged on event-driven architecture as the agent backbone (Confluent "Streaming Agents", A2A-over-Kafka, multivariate anomaly detection; LangGraph 1.0 / AutoGen v0.4 native agent primitives). Canonical pipeline: detection agent on telemetry windows → classification/correlation agent → decisioning agent → **human escalation**, all as replayable events on an immutable log. **VERIFIED**: [Confluent agentic EDA blog](https://www.confluent.io/blog/autonomous-agentic-event-driven-systems-architecture/), [Confluent Intelligence Q1-2026 update](https://www.confluent.io/blog/2026-q1-confluent-intelligence-update/), [Streaming Agents](https://www.confluent.io/blog/introducing-streaming-agents/).
- **Claude Agent SDK** — default 2026 harness for long-running tool-using agents: sessions, auto-compaction, subagents (context isolation/parallelism/tool restriction), hooks (PreToolUse/PostToolUse/Stop) as the enforcement point for audit logs and permission gates; MCP-native. **VERIFIED**: [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [production guide](https://inference.net/content/claude-agent-sdk-production-guide/).
- **Observability standard**: OpenTelemetry GenAI semantic conventions (invoke_agent / execute_tool spans, `gen_ai.client.operation.duration`, token-usage metrics) — still "Development" status but supported by Datadog/Honeycomb/New Relic and emitted by major frameworks; stable enough to build on. **VERIFIED**: [OTel GenAI observability blog](https://opentelemetry.io/blog/2026/genai-observability/), [semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai).

**Best-practice shape for "agent watches metric stream → anomaly → draft report → human approves"** (**INFERENCE**, assembled from verified patterns):
1. Stream tier (V0/V1 above) computes windows; a cheap deterministic detector (threshold/EWMA/IsolationForest) — not the LLM — watches every window.
2. Anomaly event (immutable, on the ledger) **triggers** an analysis agent run as a **DBOS durable workflow** (LLM call = one retryable step; crash-safe).
3. Agent has MCP tools: query DuckDB, read ledger, draft report artifact. Draft goes to `pending_approval` state.
4. **Human-in-the-loop gate** = a durable workflow step waiting on an approval event (DBOS supports waiting workflows; UI shows diff + evidence). Only after approval does the publish step run.
5. Every step emits OTel GenAI spans + a hash-chained ledger entry → replayable audit ("which agent did what, on which data, approved by whom").

## 4. Benchmark & stress-testing harnesses

- **API load**: **k6** (Go binary, JS-scripted, first-class thresholds, best CI story, Windows via winget/choco single binary) is the 2026 default; **Locust** (pure Python, live web UI, distributed mode, lower per-node RPS) when tests must reuse Cortex's Python client code; **oha** (Rust, TUI) / **vegeta** (constant-RPS) for quick CI smoke throughput checks. **VERIFIED**: [k6 vs Locust 2026](https://qaskills.sh/blog/k6-vs-locust-2026), [JMeter vs k6 vs Locust 2026](https://qainsights.com/jmeter-vs-k6-vs-locust-in-2026-which-load-testing-tool-should-you-pick/), [permissive-license tools mapping](https://codenote.net/en/posts/k6-alternatives-permissive-license-load-testing-tools/).
- **DuckDB under concurrency**: single process, one writer + many readers; concurrent appends never conflict, concurrent row-edits abort optimistically; multi-stream query throughput degrades ~41% at 16 parallel streams in 2026 benchmarks (internal scheduling contention) — so cap NL→SQL concurrency and measure it. DuckDB ~v1.5.x now, v2.0 expected fall 2026. **VERIFIED**: [DuckDB concurrency docs](https://duckdb.org/docs/current/connect/concurrency), [2026 benchmark blindspots](https://medium.com/@ThinkingLoop/duckdb-vs-clickhouse-2026-benchmark-blindspots-e2b59627e952). SQLite ledger: WAL mode, single-writer; storm-test batched vs per-row commits. **INFERENCE** (standard SQLite behavior).
- **Agent-pipeline latency**: no off-the-shelf harness; the standard is OTel GenAI spans end-to-end (event-ingress timestamp → invoke_agent → execute_tool → report-published) and computing p50/p95/p99 from traces; frameworks emit these natively. **VERIFIED** (OTel refs above) + **INFERENCE** on harness design.
- **Chaos-lite for one box**: the discipline is hypothesis → bounded blast radius → observe → verify SLO, not "process roulette"; heavy tools (Chaos Mesh, Litmus, krkn) are Kubernetes-oriented — overkill. For a single node, scripted `taskkill /F` (Windows) / `kill -9` mid-workflow + assert durable resume is exactly the durable-execution recovery contract (DBOS: resume from last completed step; Temporal: transparent re-execution in a new process). **VERIFIED**: [Temporal durable execution guide](https://temporal.io/blog/what-is-durable-execution), [chaos strategy guides 2026](https://oneuptime.com/blog/post/2026-01-30-chaos-testing-strategies/view); harness design **INFERENCE**.

### Concrete stress-suite design for Cortex (**INFERENCE**)

`tests/stress/` + `pytest -m stress` + a `make stress` target; k6 + Python drivers; all local:

1. **Ledger append storm** — driver spawns N processes/threads appending hash-chained entries to SQLite (WAL) and Postgres; sweep N ∈ {1,4,16,64}, batch ∈ {1,10,100}. Assert: zero lost/duplicate entries, chain verifies end-to-end, p99 append latency budget; record entries/sec.
2. **NL→SQL concurrency** — k6 scenario hitting the FastAPI query endpoint with a canned prompt corpus at 1→32 VUs; DuckDB behind a bounded connection/semaphore pool. Assert: no 5xx, p95 < budget, graceful queuing (429/queue not crash) beyond the cap; chart RPS vs p95 to find the knee (expect contention per DuckDB multi-stream data above).
3. **Streaming ingest throughput** — synthetic sensor generator POSTs (V0) or publishes to JetStream (V1) at ramped rates; measure rows/sec landed in Parquet/DuckDB, end-to-end ingest lag, and writer-batch flush latency; long-tail run for file-handle/partition growth.
4. **Chaos-lite durable resume** — start an agent pipeline workflow (ingest→analyze→report), `taskkill /F` the process at randomized step boundaries and mid-step; restart; assert workflow completes exactly once, ledger chain intact, no orphaned `pending_approval` states. Run 100 iterations in CI-nightly.
5. **Agent-pipeline soak** — 24 h run: streaming generator + scheduled anomaly injections every ~10 min triggering agent workflows (LLM stubbed with a deterministic fake for $0 + repeatability; real model in a short weekly soak). Watch RSS/VRAM growth, DuckDB file growth, OTel p95 drift, queue depth. Assert flat memory slope and zero missed anomalies.
6. **Reporting** — every run writes a JSON summary (tool versions, git SHA, machine specs, metrics) appended to a `benchmarks` DuckDB table so regressions are queryable — the platform benchmarks itself.

## Verdicts for Cortex

| Decision | Pick | Why (see sections above) |
|---|---|---|
| **Streaming V0** | FastAPI webhooks + asyncio batch writer → Parquet/DuckDB | $0, Windows-native, no new procs; DuckDB appends are conflict-free |
| **Streaming V1** | **NATS JetStream** + `nats-py` | Only broker with a native Windows single binary; replay, consumer groups, KV; ~10-20 MB |
| **Streaming V2** | **Redpanda (Docker/WSL2) + Quix Streams** | Kafka-API interop without JVM; Quix v3.24 is the one actively-backed Python processing lib |
| **P3 durable execution** | **DBOS Transact** (SQLite default → existing Postgres); Temporal = documented scale-out path | Library-not-server, MIT, v2.27 (Jul 2026), crash-resume from last step, agent-SDK integrations |
| **Agent-on-stream pattern** | Deterministic detector on windows → anomaly event → DBOS durable agent workflow with MCP tools → human-approval step → publish; OTel GenAI spans + ledger throughout | Matches 2026 production consensus (Confluent/Databricks patterns) at local-first cost |
| **Agent tool surface** | Expose Cortex ops as **MCP servers** | MCP is the Linux-Foundation-governed industry standard; any runtime can consume |
| **Stress suite** | k6 (API) + Python drivers (ledger/ingest) + taskkill chaos-lite + 24 h soak with stubbed LLM; results into a DuckDB `benchmarks` table | Section 4 design; all free, all Windows-runnable |

**Avoid**: Faust/faust-streaming (unmaintained lineage), Arroyo (post-acquisition roadmap risk), full Kafka KRaft on-box (JVM weight), Prefect/Dagster for durability (batch orchestrators + July 2026 merger churn), Kubernetes chaos frameworks (wrong scale).
