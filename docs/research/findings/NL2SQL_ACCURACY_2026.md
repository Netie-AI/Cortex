# NL→SQL Accuracy Research — Findings (as of 2026-07-20)

Research for Cortex DMS: 6-table closed warehouse schema, ~25k rows, DuckDB, sqlglot guard,
semantic layer at `packs/dms/semantic_layer.yaml`. Goal: ~99% answer accuracy, ZERO confident wrong answers.
Tags: **[V]** = verified against primary source; **[R]** = reported by secondary source, not independently verified; **[I]** = inference/recommendation.

---

## 1. State of the art (BIRD / Spider 2.0, mid-2026)

- **[V] BIRD leaderboard (fetched 2026-07-20, https://bird-bench.github.io/):** top test-set execution accuracy (EX):
  1. AskData + GPT-4o (AT&T) — **81.95%** (2025-09-25)
  2. Agentar-Scale-SQL (Ant Group) — **81.67%** (2026-06-19)
  3. Sber Text2SQL — **81.33%** (2026-05-27)
  4. Xiaomi Text2SQL — **80.83%** (2026-07-14)
  5. DeepEye (HKUST-GZ) — **79.09%** (2026-07-04)
  Human performance: **92.96%**. So SOTA ≈ 88% of human on a messy open benchmark; progress has plateaued around 80-82% for a year.
- **[R]** Google "Gemini-SQL2" (announced ~2026-06-12 per secondary blogs) claims ~80% BIRD EX; not on the official leaderboard — treat as unverified marketing-adjacent.
- **[V] Spider 2.0 (fetched 2026-07-20, https://spider2-sql.github.io/):** 632 real enterprise text-to-SQL workflow problems (schemas >1,000-3,000 columns, 100+ line SQL, multiple dialects). Tracks: Spider 2.0-Snow top ≈ **96.7** (Genloop Sentinel Agent v2 Pro — agentic, huge jump from ~30-40% in 2025); Spider 2.0-Lite top **73.67** (ktx/Kaelio); Spider 2.0-DBT (DuckDB) top **65.6** (SignalPilot Agent).
- **[V] Techniques used by top systems:** schema linking; multi-path candidate generation + selection. CHASE-SQL (Google Cloud/Stanford, ICLR 2025, https://arxiv.org/abs/2410.01943): divide-and-conquer + query-plan CoT + instance-aware few-shot to generate diverse candidates, then a fine-tuned **binary pairwise selection agent** — which **beats plain self-consistency voting** — 73.0% BIRD test at submission. Successors: JudgeSQL (weighted consensus tournament, arXiv 2510.15560), SIRIUS-SQL (execution-feedback anchoring, arXiv 2606.01246), ReEx-SQL (execution-aware RL, arXiv 2505.12768). Common thread: **test-time compute + execution-grounded selection**, not bigger single-shot models.
- **Why a small closed schema does far better:**
  - **[V]** MotherDuck analysis (https://motherduck.com/blog/bird-bench-and-data-models/): models scoring 58-64% strict EX on BIRD reach **~94-95% under realistic evaluation** (benchmark annotation errors + acceptable formatting differences account for the gap); simple schemas (~7 tables, clear joins) needed almost no extra context; core claim: "good data modeling *is* the semantic layer."
  - **[V]** CIDR 2026: "Text-to-SQL Benchmarks are Broken" (https://www.vldb.org/cidrdb/papers/2026/p5-jin.pdf) — large fraction of benchmark "errors" are annotation errors, i.e. published SOTA understates achievable accuracy on clean schemas.
  - **[V]** dbt dev-blog benchmark (2026-04-07, https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026): on a 15-table insurance schema, raw text-to-SQL 84.1-90.0% vs **98.2-100% via semantic layer** (11 questions × 20 runs; small n, but directionally consistent).
  - **[I]** BIRD/Spider difficulty comes from: huge/dirty schemas, ambiguous questions, missing business definitions, annotation noise. Cortex DMS has none of these: 6 tables, curated joins/glossary, single dialect (DuckDB), controllable question surface. 95-99%+ is a reasonable ceiling here even for small models — the binding constraint is *verification and abstention discipline*, not raw generation ability.

## 2. Semantic-layer / certified-metrics approach (the key pattern)

### Snowflake Cortex Analyst
- **[V] Semantic model YAML** (https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst/semantic-model-spec): **logical tables** over base tables (db/schema/table); **dimensions** with `name, synonyms[], description, expr, data_type, unique`; time dimensions; **measures/facts** (aggregatable); filters; **`sample_values`** per column — "should include any values likely to be referenced in user questions" (drives entity/value grounding); enforced dimension-vs-measure dichotomy.
- **[V] Verified Query Repository** (https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst/verified-query-repository): `verified_queries:` entries with `name, question, sql, verified_at, verified_by, use_as_onboarding_question`. Verified SQL must use **logical** (semantic-layer) names, not physical columns. At inference, matching VQR entries are used, and the API's **confidence field** reports which verified query was used. Snowflake also ships an optimizer that mines verified queries to improve the semantic model (https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-analyst/analyst-optimization).
- **[V] Accuracy claims** (https://www.snowflake.com/en/blog/cortex-analyst-ai-self-service-analytics/, engineering blog "Behind the Scenes"): **~90%+ SQL accuracy** on real-world evals; ~2x single-prompt GPT-4o; ~14% above competing solutions. Architecture is **agentic**: a **classification agent** buckets questions (ambiguous / non-data / non-SQL / answerable) and **rejects everything not unambiguously answerable, suggesting answerable alternatives instead** — i.e., their headline accuracy is *conditional on answering*; abstention is a first-class feature.

### Databricks AI/BI Genie
- **[V] Grounding assets** (https://docs.databricks.com/en/genie/trusted-assets.html, https://docs.databricks.com/aws/en/genie/best-practices): plain-text **instructions**; **example SQL queries** (question + SQL pairs); **trusted assets** = *parameterized* example SQL queries and SQL UDFs — when one answers a question, the response is **labeled "trusted"** and shows the argument values used; **value dictionaries / sample values** for categorical columns (exact-match filtering); explicit **joins with cardinality**; metric views for shared logic.
- **[V] Best practices** (https://www.databricks.com/blog/data-dialogue-best-practices-guide-building-high-performing-genie-spaces): denormalize/pre-join, pre-calculate common fields, synonyms for business jargon, keep general instructions minimal, establish benchmarks early with SME ground truth, monitor real usage and fold failures back in.
- **[V] Built-in benchmarks** (https://docs.databricks.com/aws/en/genie/benchmarks): author golden questions with a canonical SQL whose **result set** is the answer; Genie runs them as fresh conversations and **compares result sets** (see §4 for scoring); up to 500 questions; recommend 2-4 phrasings per question.

### dbt Semantic Layer / MetricFlow, Cube
- **[V]** MetricFlow (open-sourced Apache 2.0 late 2025, https://www.getdbt.com/blog/open-source-metricflow-governed-metrics): metrics/dimensions/semantic models in YAML; **deterministic, grain-aware SQL compiled at query time** — the LLM asks for a metric by name, never writes joins. dbt internal testing: **83% NL accuracy with semantic layer vs ~40% raw SQL over undecorated tables**; dev-blog benchmark 98.2-100% vs 84.1-90% (above). Key quote-worthy finding: semantic layer "fails loudly with error messages" while raw text-to-SQL "fails silently with wrong numbers."
- **[V]** Cube (https://cube.dev/articles/semantic-layer-for-ai-agents-2026): LLM **selects from predefined metrics and dimensions; the semantic layer generates the SQL**; exposed via SQL/REST/GraphQL/MCP. Vendor claim: ~3x accuracy, 95%+ reliability on a 522-query workload **[R]**.

### The common design (all four vendors converge)
- **[V/I]** NL → *(intent classification + entity/value resolution via synonyms & sample values)* → **governed metric / parameterized template** → **deterministic SQL compile** → execute. Free-form LLM SQL exists only as a fallback, behind verification, and answers from it are visually distinguished from "trusted/certified" answers. A **verified-query repository** feeds few-shot retrieval AND regression tests. Ambiguous → **reject + suggest answerable questions**, never guess.

## 3. Verification & abstention techniques

- **Execution-based verification [V]:** run the SQL before answering; regenerate/repair on error. Execution feedback in the loop is now standard (SIRIUS-SQL, ReEx-SQL above). Genie scores empty-result/error as automatic "Bad."
- **Self-consistency over executed results [V]:** sample N candidates, execute all, **vote on the result set** (not the SQL text); agreement rate is a cheap, well-tested confidence signal. CHASE-SQL showed a trained pairwise selector beats naive voting, but voting alone already recovers most of the gain (https://arxiv.org/abs/2410.01943).
- **SQL equivalence checking [V]:** formal tools — VeriEQL (bounded equivalence w/ integrity constraints, arXiv 2403.03193), SQLSolver (LIA*-based; proved 346/359 Calcite/Spark rewrite pairs), SPES (bag semantics; no MAX/MIN, date functions), QED; SpotIt applies formal verification to text-to-SQL *evaluation* (arXiv 2510.26840). **[I]** For Cortex: overkill at runtime; useful offline to dedupe/canonicalize the golden set. Runtime equivalence = "same executed result set."
- **Constrained decoding [V]:** PICARD (arXiv 2109.05093 line of work) — incremental parser constrains generation to schema-valid SQL; **T5-Base + PICARD outperformed unconstrained T5-Large**, i.e., grammar constraints buy small models a size class. Modern equivalents: grammar-guided structured output (llama.cpp/vLLM GBNF/outlines; NVIDIA showed the same effect for small-model bash generation). **[I]** With sqlglot already in the loop, the cheap version is post-hoc: parse → validate tables/columns/functions against the semantic layer allowlist → reject/repair. Full constrained decoding is a T0 upgrade option.
- **Confidence estimation & abstention [V]:**
  - TrustSQL (arXiv 2403.15879): benchmark scoring *reliability* — correct SQL for feasible questions AND abstention on infeasible ones, with **penalty-based scoring** (a confident wrong answer costs more than an abstention). Finding: high scores under severe penalties are hard; pipeline approaches (generator + infeasibility detector + error detector) are the practical route.
  - Error-detection study (arXiv 2501.09527): entropy-based confidence + **Gaussian Mixture selective classifier** gave the best coverage/risk trade-off, ~80% risk reduction, AUC up to 0.93 — but **only under minimal distribution shift**; detecting *unanswerable questions* is easier than detecting *wrong SQL*; isotonic calibration essential.
  - Broader method comparison incl. syntax-aware logit aggregation: arXiv 2508.14056.
  - **[I]** Practical stack-ranked signals for Cortex: (1) which layer answered (certified > template > free-form); (2) N-candidate executed-result agreement; (3) entity-resolution completeness (every noun mapped to a glossary/sample value?); (4) token-level confidence last. Clarify when: an entity fails to resolve, two glossary terms both match, a date range/unit is unstated and materially changes the answer, or candidate agreement < threshold.
- **Sanity rails [I, informed by Genie's scoring rules]:** post-execution checks before answering — empty result on a "how many/which" question → suspicious, confirm intent; row count vs table cardinality bounds; NULL-heavy aggregates; percentages outside 0-100; negative stock; `SUM` over a column that the semantic layer marks non-additive; result magnitude vs historical answer range for the same metric.
- **Unit & date pitfalls [I, schema-specific]:** everything in this schema is `_kg` — always state the unit in the answer; capacity utilisation is a ratio ×100 — never double-multiply; "expired" vs "expiring soon" need explicit date windows; unstated time ranges ("recent shipments") must be echoed back as an assumption or clarified; DuckDB `CURRENT_DATE` vs data freshness (state the as-of date).

## 4. Evaluation harness design

- **[V] Genie's benchmark scoring is the best public template** (https://docs.databricks.com/aws/en/genie/benchmarks): golden question + canonical SQL; compare **executed result sets**, not SQL text. Rating: **Good** = exact SQL match, OR matching result sets, OR same data different sort order, OR numeric values equal when rounded to **4 significant digits**. **Bad** = empty/error results, extra columns, or differing single-cell values. Else → manual review. Up to 500 questions; author **2-4 phrasings per question**; re-run after every data/instruction change.
- **Execution-match vs result-match [V]:** strict string/AST match produces false negatives (aliases, ordering, formatting, extra columns) — use result-set match with tolerance rules (ETM, arXiv 2407.07313; SpotIt for formal rigor). MotherDuck's 58-64% → 94-95% swing (§1) is exactly this effect plus annotation errors — so **audit your own golden SQL as hard as the model's**.
- **LLM-as-judge pitfalls [V]** (Arize/Phoenix, https://arize.com/blog/text-to-sql-evaluating-sql-generation-with-llm-as-a-judge/): notable false positives/negatives; counter-intuitively, **adding the schema to the judge prompt made judging worse**; position/verbosity bias need controls. **[I]** For a closed schema with canonical SQL available, deterministic result-set comparison should be the primary metric; LLM-judge only for the natural-language *presentation* of the answer, never for numeric correctness.
- **[I] Eval-set size for a 6-table schema** (no published formula exists; triangulated from Genie's 500-cap/quality-over-quantity guidance and dbt's too-small 11-question set): start at **~120-180 golden questions**: every glossary term (~11) × 2-3 phrasings; every join path (~10 in the YAML) exercised; per-table aggregates/filters/rankings; ~15 multi-hop questions; **15-20% adversarial**: unanswerable (data not in schema), ambiguous (two valid readings), trick units/dates, empty-result-is-correct cases. Each entry: `question, canonical_sql, expected_result (or generator), tolerance (sort-insensitive; numeric 4 sig figs; column superset allowed: no), expected_behavior (answer | abstain | clarify)`. Run answerable questions ≥3× to measure variance (dbt used 20 runs/question).
- **[I] CI regression gate:** the suite runs on every semantic-layer, prompt, template, or model change. Gate: (a) **zero** previously-passing questions fail; (b) **zero confident-wrong** on the full suite — a wrong result delivered without a "generated, unverified" flag fails the build; (c) abstention on answerable questions is a soft warning (coverage metric), never a hard failure. Score with a TrustSQL-style penalty metric: correct +1, abstain 0, wrong-confident −k (k≥1) — this makes "guessing" strictly irrational for the system.

## 5. Small-model reality check (7-8B local, T0/T1)

- **[R] Qwen3-8B:** ~73.6% BIRD-dev EX, ~77.2% Spider-dev EX (community NL2SQL-Benchmark harness, https://github.com/Artessay/NL2SQL-Benchmark) — competitive general-purpose baseline.
- **[V] Arctic-Text2SQL-R1-7B** (Snowflake, arXiv 2505.20315, Apache-2 weights on HF): **68.9% BIRD-dev / 68.5% BIRD-test**, 57.2% avg across six benchmarks; matched 70B-class ExCoT; the only 7B in the BIRD top tier at release (May 2025). Trained with execution-correctness RL — evidence that execution-grounded training, not scale, drives SQL ability.
- **[V] OmniSQL-7B** (VLDB 2025, arXiv 2503.02240): **87.9% Spider-test EX greedy**, beating DAIL-SQL+GPT-4+self-consistency (86.6%); trained on SynSQL-2.5M. Spider's clean, modest schemas are the closest public analogue to Cortex's 6-table schema → **~88% free-form EX at 7B on a Spider-like schema is demonstrated**, before semantic-layer help, few-shot verified queries, voting, or repair loops.
- **[V] XiYanSQL-QwenCoder-32B:** 67.0 dev / 69.0 test BIRD — 32B class, useful as an optional bigger tier.
- **[I] What this means for Cortex:** a Qwen3-8B-class model with (a) full semantic-layer context incl. synonyms + sample values, (b) 3-5 retrieved verified queries as few-shot, (c) 3-5 sampled candidates with executed-result voting, (d) sqlglot validation + one repair round, should land **~90-97% EX on free-form** over this schema. That is *not* 99% — which is exactly why free-form must be the last resort, not the main path.
- **[I] Template/slot-filling beats free-form at T0/T1 — yes, decisively.** Evidence chain: dbt's 98-100% when the LLM only picks metric+dimensions (§2); PICARD showing constraints buy a size class (§3); Cortex Analyst/Genie both routing to verified/trusted assets first. Intent classification + slot extraction is a far easier task for an 8B model than SQL synthesis, and the compiled SQL is correct by construction. Small models should mostly *choose*, rarely *write*.

## Verdicts for Cortex

**Recommended architecture — four layers, strictly ordered (answer at the first layer that fires):**
1. **L0 Certified answers:** verified-query repository (Cortex-Analyst-style YAML block: `name, question, sql, verified_at, verified_by`) with embedding/paraphrase matching. Deterministic replay, badge as "certified." Also mine these as few-shot for L2.
2. **L1 Governed metrics + templates:** compile the existing glossary (`low stock`, `capacity utilisation`, `expired`, `delayed shipment`, …) into parameterized SQL templates (Genie "trusted assets" pattern). T0/T1 model does **intent + slot filling only** (metric, dimensions, filters, date range, top-N); entities resolve against sample-value dictionaries per column; SQL is compiled deterministically. Unresolvable slot → clarify.
3. **L2 Verified free-form:** 8B-class model (Qwen3-8B baseline; consider Arctic-Text2SQL-R1-7B or OmniSQL-7B as a SQL-specialist tier), semantic-layer prompt + retrieved verified queries; sample 3-5 candidates → sqlglot parse + allowlist → execute all → **result-set majority vote** → sanity rails (§3) → answer badged "generated — verify before relying on it," always showing SQL + applied filters/date range/units. Disagreement or rail failure → escalate to larger model or L3.
4. **L3 Abstain/clarify:** classification-agent pattern from Cortex Analyst — reject ambiguous/non-data/out-of-schema questions and **suggest 2-3 nearby answerable questions** (from L0/L1 catalog). This converts abstention from a dead end into navigation.

**Eval set:** ~120-180 golden questions as specified in §4 (glossary × phrasings, all join paths, 15-20% adversarial/unanswerable), Genie-style result-set scoring (sort-insensitive, 4-sig-fig numeric tolerance), ≥3 runs per answerable question, TrustSQL-style penalty scoring, CI gate = zero regressions + zero confident-wrong. Every user-corrected or SME-validated answer graduates into both the VQR (L0) and the eval set.

**Realistic accuracy targets [I]:** L0 ≈ 100% (deterministic); L1 ≥ 98% end-to-end (residual errors = slot-filling mistakes → caught by clarification rules); L2 ≥ 90% raw, ≥ 97% precision *after* voting + rails + badging; overall: **≥ 99% of delivered answers correct, 5-15% of questions ending in clarify/abstain** — and that abstention rate is the price of the zero-wrong guarantee. Track *coverage* and *answered-accuracy* as separate dashboard metrics; push coverage up over time by promoting L2 wins into L0/L1, never by loosening gates.

**Top 5 implementation rules for "no confident wrong answers":**
1. **The LLM never writes SQL that reaches the user unverified.** Deterministic layers (L0/L1) answer most questions; L2 output must pass parse → allowlist → execution → vote → sanity rails, and is visibly badged as generated, with its SQL shown.
2. **Abstain-by-default on resolution failure.** Any unmapped entity, ambiguous glossary hit, or unstated material parameter (date range, unit, location scope) triggers clarification — echo the assumption or ask, never silently default.
3. **Score guessing as worse than silence.** Penalty-based eval (wrong-confident = −1+, abstain = 0) in CI, gate on zero confident-wrong; this shapes every threshold-tuning decision in the right direction.
4. **Result-set truth, not SQL-text truth.** Verify and evaluate by executing against DuckDB with tolerance rules; audit golden SQL itself (benchmark-annotation errors caused 30+pp of "model error" on BIRD).
5. **Close the loop.** Log every question + SQL + result; SME-review failures weekly; promote fixes to verified queries and eval cases. Cortex Analyst, Genie, and dbt all converge on this: the semantic layer + VQR *is* the accuracy system, and it compounds.
